# Scenario Script

## Role

`flagship scenario writer #2`

## Scenario Title

`트래픽 급증으로 DB 과부하`

## Battle Goal

플레이어는 트래픽 급증 상황에서:

- 사용자 영향이 큰 경로를 먼저 식별하고
- 병목이 진짜 DB인지 빠르게 좁히고
- 잘못된 대응이 어떻게 장애를 키울 수 있는지도 함께 고려하며
- 즉시 완화와 장기 개선을 구분해서 말해야 한다

이 시나리오는 `scale out만 외치는 답변`보다 `영향 파악 -> 병목 분리 -> 완화 -> 재발 방지`의 순서를 훈련시키는 데 초점을 둔다.

## Incident Brief

`점심 프로모션 푸시 발송 5분 후, 홈 피드와 상품 상세 조회 트래픽이 평소의 8배까지 치솟았습니다. 메인 조회 API의 p95는 120ms에서 1.8s로 상승했고, 모바일 앱 사용자의 18%가 첫 화면 진입 이후 3초 넘게 기다리고 있습니다. 앱 서버 CPU는 40% 수준으로 높지 않지만 Aurora read latency는 35ms에서 780ms까지 뛰었고, read replica connection 수도 빠르게 차오르는 중입니다. 지금은 점심 피크 시간대라 홈 피드와 상품 상세를 오래 느리게 둘 수 없습니다.`

## Realism Anchors

### Time Context

- `평일 12시 05분`
- `마케팅 팀이 12시 정각에 30만 명 대상 푸시를 발송한 직후`

### User Impact Surface

- 모바일 앱 `홈 피드`
- `상품 상세 조회`
- 장바구니 진입 전 탐색 흐름

주문/결제 API는 아직 정상이라, 핵심 수익 흐름은 완전히 멈추지 않았지만 유입 상단이 막히면 곧 전환에도 영향이 간다.

### Measurable Symptoms

- 홈 피드 API p95: `120ms -> 1.8s`
- 상품 상세 API p95: `180ms -> 2.4s`
- 모바일 첫 화면 이탈률: `평소 6% -> 19%`
- Aurora read latency: `35ms -> 780ms`
- read replica active connections: `평소 220 -> 890`
- 캐시 hit rate: `92% -> 61%`

### Contradictory Clues

- 앱 서버 CPU는 `40%` 수준으로 높지 않다
- 쓰기 쿼리 비중이 큰 주문/결제는 아직 정상이다
- 에러율은 크지 않지만 `지연`이 급격히 증가하고 있다

즉 `앱 서버 증설`이나 `DB 장애 단정`이 모두 성급한 답이 될 수 있다.

### Constraint

- 지금은 `점심 피크 시간대`라 사용자 체감 지연을 오래 방치하기 어렵다
- 캐시 TTL은 방금 시작한 캠페인 배너/랭킹 노출 때문에 짧아져 있다
- 광고 예산이 이미 집행 중이라 유입 자체를 바로 끊기는 어렵다

### Risk Of The Wrong Move

- 무분별한 앱 서버 scale-out은 DB read pressure만 더 밀어 올릴 수 있다
- 캐시를 성급히 flush하면 miss 폭증으로 읽기 부하가 더 커질 수 있다
- 홈 피드 전체 기능을 내리면 주문은 살아 있어도 전환율 급락과 CS 증가로 이어질 수 있다

## Starting States

### `과부하`

- 짧은 설명: 요청이 한꺼번에 몰려 시스템이 버거워하고 있다.
- 면접 의미: 무작정 증설보다 어떤 구간이 가장 크게 느려졌는지 먼저 좁혀야 한다.

### `핵심 시간대`

- 짧은 설명: 지금은 장애 허용도가 낮다.
- 면접 의미: 완벽한 원인 분석보다 빠른 완화와 핵심 흐름 보호가 중요하다.

### `흐린 로그`

- 짧은 설명: 모든 단서가 명확하게 보이지는 않는다.
- 면접 의미: 숫자는 많지만 원인을 단정할 만큼 충분한 관측이 아닐 수 있다.

## Turn 1

### State Reveal

- `전장에 과부하가 몰아친다!`
- `점심 프로모션 푸시 이후 유입이 한꺼번에 쏟아지고 있다.`
- `핵심 시간대다!`
- `지금은 짧은 복구 시간 자체가 점수가 된다.`
- `흐린 로그가 전장을 스친다!`
- `지표는 쌓이고 있지만, 병목을 단정하기엔 아직 이르다.`

### Interviewer Attack

- `면접관의 추궁!`
- `"이 상황에서 가장 먼저 무엇을 확인하시겠습니까? 그리고 왜 그 순서가 지금 맞다고 보시나요?"`

### Candidate Actions

- `범위 파악`
- `우선순위 선언`
- `관측 세우기`
- `원인 분리`

### Strong Player Answer Example

`우선 홈 피드와 상품 상세처럼 유입 상단의 핵심 읽기 흐름이 어디까지 느려졌는지부터 확인하겠습니다. 주문과 결제가 아직 정상인지 같이 봐서 영향 범위를 나누고, 동시에 앱 서버 자원과 DB read latency, 캐시 hit rate를 함께 비교해 병목이 앱인지 캐시 미스인지 DB 읽기인지부터 분리하겠습니다.`

### Why This Is Strong

- 사용자 영향부터 본다
- 홈 피드/상품 상세와 주문/결제를 분리해 본다
- DB 과부하를 바로 단정하지 않고 병목을 분리한다
- CPU가 높지 않다는 모순 단서를 반영한다

### Common Mistakes

- `앱 서버부터 늘리겠습니다`처럼 잘못된 계층을 먼저 건드린다
- `DB가 느리네요`처럼 read pressure, 캐시 미스, 핫 키 여부를 구분하지 않는다
- 사용자 영향 없이 CPU, 메모리, 쿼리 얘기만 길게 한다
- 캠페인 유입을 바로 끊는다고 말해 비즈니스 제약을 무시한다

### Follow-up Question 1

- `면접관의 되물림!`
- `"앱 서버 CPU는 높지 않은데 read latency만 치솟고 있습니다. 이걸 근거로 무엇을 더 확인하면 캐시 문제인지, DB read pressure인지, 특정 조회 쿼리 문제인지 나눌 수 있습니까?"`

## Turn 2

### New Reveal

- `느린 저장소가 모습을 드러냈다!`
- `상품 상세 API에서 특정 read query의 p95가 2.9s까지 치솟았다.`
- `확산 조짐이 보인다!`
- `홈 피드 fallback도 느려지기 시작해 탐색 흐름 전체가 흔들리고 있다.`
- `추가 정보가 드러났다!`
- `캐시 hit rate가 92%에서 61%로 떨어졌고, 캠페인 랭킹 계산 결과가 30초 TTL로 자주 재조회되고 있다.`

### Interviewer Attack

- `면접관의 압박!`
- `"핫 경로가 조회성 read pressure와 캐시 미스에 동시에 물리고 있어 보입니다. 지금 어떤 완화 조치를 먼저 하시겠습니까? 그리고 어떤 조치는 오히려 위험할까요?"`

### Candidate Actions

- `우선 차단`
- `즉시 우회`
- `의존성 점검`
- `상황 공유`

### Strong Player Answer Example

`우선 캠페인 랭킹, 개인화 추천처럼 비핵심 읽기 기능부터 임시로 단순화해 DB read pressure를 줄이겠습니다. 홈 피드와 상품 상세는 캐시 가능한 공통 응답으로 degraded mode를 열고, TTL을 무작정 flush하지 않고 오히려 짧은 구간에서 read-through 캐시와 hot key 보호를 먼저 보겠습니다. 동시에 어떤 query pattern이 replica를 가장 세게 치는지 추적해 핵심 구매 흐름이 흔들리기 전에 부하를 낮추겠습니다.`

### Why This Is Strong

- 전체 서비스를 막지 않고 비핵심부터 제한한다
- 캐시 flush 같은 위험한 조치를 피한다
- 완화와 진단을 병행한다
- 핵심 구매 흐름 보호를 명시한다

### Common Mistakes

- 서비스 전체를 막자고 한다
- 슬로우 쿼리 확인 같은 진단만 말하고 즉시 완화가 없다
- 캐시를 비우거나 replica를 더 붙이면 끝난다고 단순화한다
- 비핵심 기능과 핵심 탐색 흐름을 구분하지 않는다

### Follow-up Question 2

- `면접관의 압박감이 짙어진다!`
- `"만약 degraded mode를 열어도 read latency가 충분히 내려오지 않는다면, 어떤 기능을 다음으로 희생하고 어떤 지표를 기준으로 그 결정을 내리시겠습니까? 반대로 절대 건드리지 않을 흐름은 무엇인가요?"`

## Turn 3

### New Reveal

- `복구 창이 열렸다!`
- `랭킹과 개인화 영역을 단순화한 뒤 홈 피드 p95가 620ms까지 내려왔다.`
- `불만 누적이 남아 있다.`
- `앱 리뷰와 CS에는 “처음 화면이 너무 늦다”는 불만이 쌓이고 있다.`
- `가설 붕괴의 흔적도 남아 있다.`
- `전체 DB 장애라기보다 특정 조회 패턴과 TTL 설계가 트래픽 급증에 취약했던 것으로 보인다.`

### Interviewer Attack

- `면접관의 마무리 승부수!`
- `"서비스가 일단 버티기 시작했다면, 진짜로 복구됐다고 무엇으로 판단하시겠습니까? 그리고 다음 캠페인 때 같은 문제가 다시 와도 DB가 먼저 무너지지 않게 하려면 무엇을 바꾸시겠습니까?"`

### Candidate Actions

- `상황 공유`
- `관측 세우기`
- `원인 분리`
- `사후 정리`

### Strong Player Answer Example

`우선 홈 피드와 상품 상세의 p95, 첫 화면 이탈률, replica connection 수, 캐시 hit rate가 실제로 안정 구간에 들어왔는지 확인하겠습니다. 그다음 이번 장애가 전체 DB 용량 부족이 아니라 특정 조회 패턴과 짧은 TTL 설계, 캠페인 유입이 겹치며 생긴 read pressure였는지 정리하겠습니다. 재발 방지로는 이벤트 전용 캐시 전략, hot key 보호, 비핵심 조회의 기능 강등 스위치, 읽기 경로 부하 테스트 기준을 보강하고, 마케팅 팀과도 피크 유입 제어 기준을 맞추겠습니다. 사용자 공지와 내부 회고도 함께 진행하겠습니다.`

### Why This Is Strong

- 복구 확인 지표를 말한다
- 원인을 `전체 DB 부족`으로 뭉개지 않는다
- 병목 원인 정리와 예방을 구분한다
- 사용자 커뮤니케이션과 타 부서 협업까지 포함한다

### Common Mistakes

- `다음엔 서버를 더 크게 준비하겠습니다`처럼 인프라 증설만 말한다
- 복구 확인 없이 회고부터 말한다
- 사용자 공지나 내부 공유를 완전히 빼먹는다
- 캠페인성 트래픽을 서비스 구조가 아니라 운영 실수로만 치부한다

### Follow-up Question 3

- `면접관의 마지막 되물림!`
- `"단순 증설 말고, 다음 주 같은 규모 캠페인이 다시 와도 홈 피드와 상품 상세의 read pressure가 DB에 바로 꽂히지 않게 만들 가장 현실적인 개선 한 가지를 꼽는다면 무엇입니까? 그리고 그걸 왜 1순위로 두시겠습니까?"`

## Total Follow-up Count

- 총 `3개`
- 권장 리듬:
  - 1턴 후 1개
  - 2턴 후 1개
  - 3턴 후 1개

MVP에서는 매 턴 1개를 넘기지 않는 편이 좋다. 그래야 전투 템포와 입력 피로가 무너지지 않는다.

## Scoring Intent

이 시나리오에서 특히 높게 보는 포인트:

- `영향 파악`: 핵심 사용자 흐름을 먼저 언급했는가
- `우선순위`: 완화와 진단의 순서를 분명히 했는가
- `기술적 추론`: 앱/DB/캐시/트래픽 병목을 분리해 봤는가
- `대응 적합성`: 전체 차단보다 제한적 완화와 보호 전략을 말했는가
- `설명 명확성`: 짧고 구조적으로 말했는가

특히 가산점을 주는 신호:

- `홈 피드/상품 상세`와 `주문/결제`를 분리해 말함
- `앱 서버 CPU는 높지 않다`는 모순 단서를 활용함
- `캐시 flush`, `무작정 scale-out` 같은 위험한 조치의 부작용을 짚음
- `degraded mode`, `기능 강등`, `hot key 보호` 같은 현실적 완화책을 언급함

## Final Coaching Points

- 트래픽 급증 상황에서는 `무조건 증설`보다 `핵심 경로 보호`가 먼저다.
- DB 병목처럼 보여도 처음부터 원인을 단정하지 말고 `영향 범위`, `캐시 상태`, `읽기 경로 병목`을 분리해서 말하는 편이 강하다.
- 좋은 답변은 `영향 파악 -> 완화 -> 원인 축소 -> 복구 확인 -> 예방` 순서를 갖는다.
- 핵심 시간대 시나리오에서는 기술적 정밀함보다 `빠른 피해 축소 판단`이 더 높은 점수를 받는다.
- 현실감 있는 좋은 답변은 `잘못 건드리면 더 나빠질 수 있는 조치`를 함께 언급한다.
