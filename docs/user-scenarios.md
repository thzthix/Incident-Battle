# 사용자 시나리오

## 왜 필요한가

필요하다. 게임 기획에서는 `전투 시나리오`만큼 `사용자 시나리오`도 중요하다.

전투 시나리오는 게임 안에서 무슨 사건이 벌어지는지 정리하는 문서고, 사용자 시나리오는 유저가 이 제품을 왜 열고, 어떻게 한 판을 시작하고, 어디서 만족하거나 이탈하는지 정리하는 문서다.

이 문서가 있어야:

- 첫 화면이 무엇을 해야 하는지 정해지고
- 튜토리얼이 필요한지 판단되고
- 한 판 길이와 꼬리질문 수를 무리 없이 조절할 수 있다

## 핵심 사용자 유형

### 사용자 1: 면접 직전 지원자

- 목적: 짧게 1판 돌면서 감각을 끌어올리고 싶다.
- 기대: 5분 안에 끝나고, 바로 코칭을 받는다.
- 위험: 글을 너무 길게 써야 하거나, 설명이 복잡하면 이탈한다.

### 사용자 2: 반복 연습형 지원자

- 목적: 비슷한 상황을 여러 번 돌리며 답변 순서를 익힌다.
- 기대: 같은 시나리오라도 조금씩 달라지는 상태 조합이 있다.
- 위험: 매 판이 너무 비슷하거나, 피드백이 매번 똑같으면 질린다.

### 사용자 3: 포트폴리오형 창작자

- 목적: 친구에게 보여줄 만큼 재미있는 배틀 연출을 원한다.
- 기대: 포켓몬풍 감성, 도트, 텍스트박스, 전투 리듬이 살아 있다.
- 위험: 그냥 폼 입력 사이트처럼 보이면 실망한다.

## 대표 사용자 흐름

### 흐름 1: 빠른 연습

1. 사용자가 사이트에 들어온다.
2. 회사 이름을 입력한다.
3. `연습전`을 누른다.
4. 추천 대표 시나리오 3개 중 하나를 고른다.
5. 3턴 배틀을 플레이한다.
6. 총점과 코칭을 본다.
7. 바로 재도전하거나 다른 시나리오를 누른다.

성공 기준:

- 첫 진입부터 30초 안에 전투가 시작된다.
- 한 판은 4~6분 안에 끝난다.
- 결과 화면에서 `내가 왜 이 점수인지`를 바로 이해한다.

### 흐름 2: 약점 보완 연습

1. 사용자가 지난 결과에서 `외부 API 대응이 약함`을 본다.
2. `결제 또는 외부 API 장애` 시나리오를 다시 선택한다.
3. 상태 설명을 짧게 복습한다.
4. 다시 3턴을 돌린다.
5. 이전보다 나아진 점을 확인한다.

성공 기준:

- 재도전 동기가 생긴다.
- 개선 포인트가 추상적이지 않다.

### 흐름 3: 첫 사용자 튜토리얼

1. 사용자가 처음 접속한다.
2. `튜토리얼 배틀`을 시작한다.
3. 상태 2개와 행동 선택 방식을 배운다.
4. 1턴만 짧게 체험하거나 3턴 완주를 한다.
5. 이후 실제 시나리오로 넘어간다.

성공 기준:

- 포켓몬을 몰라도 규칙이 이해된다.
- 주관식 입력이 어디까지 필요한지 감이 온다.

## MVP UX 결정

- 첫 버전은 `연습전` 중심으로 간다.
- 회사 이름 입력은 시작 화면에 둔다.
- 회사 이름은 상대 면접관의 대사와 타이틀에만 반영한다.
- 첫 플레이는 `튜토리얼 1판` 또는 `대표 시나리오 1판`으로 바로 진입시킨다.

## 한 판 길이 규칙

- 인트로: 15~25초
- 각 턴: 45~75초
- 결과 화면: 20~40초
- 총합: 4~6분

이 범위를 넘기면 반복 플레이가 무거워진다.

## 턴 설계 규칙

- 총 3턴이 기본이다.
- 턴마다 플레이어는 행동 1개를 고른다.
- 행동 뒤에는 1~2문장만 입력하게 한다.
- 너무 긴 답변은 오히려 면접 연습 UX를 해친다.

## 꼬리질문 설계 규칙

- MVP 기본: 총 2개
- 대표 시나리오 또는 어려운 시나리오: 총 3개까지 허용
- 한 턴에 꼬리질문은 최대 1개
- 1턴과 2턴에는 가급적 넣고, 3턴은 선택적으로 넣는다.

이유:

- 매 턴 여러 번 캐묻기 시작하면 게임 템포가 무너진다.
- 꼬리질문은 `압박 연출`이어야지 `심문 시뮬레이터`가 되면 안 된다.

## 지금 기준 추천값

- 튜토리얼: 꼬리질문 1개
- 일반 시나리오: 꼬리질문 2개
- 대표 하드 시나리오: 꼬리질문 3개

## 구현 전 꼭 필요한 판단

- 결과 화면에 이전 플레이와 비교를 넣을지
- 시나리오 선택 전에 난이도 표기를 넣을지
- 처음에는 회사별 말투 차이를 줄지

이 셋은 구현 직전에 다시 결정하면 된다.
