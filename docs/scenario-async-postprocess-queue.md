# Scenario Script

## Role

`flagship scenario writer #4`

## Scenario Title

`결제 후처리 큐 적체와 중복 리스크`

## Battle Goal

플레이어는 결제 승인 이후의 비동기 후처리 장애에서:

- 동기 승인과 비동기 후처리를 분리해서 보고
- 고객 신뢰와 데이터 정합성을 같이 다루고
- 큐 적체를 단순 처리량 문제로만 보지 않고
- 재처리, 멱등성, 중복 적립 리스크를 함께 설명해야 한다

이 시나리오는 `큐가 쌓였으니 consumer를 늘리겠다` 수준의 답보다 `영향 구분 -> 안전한 완화 -> 정합성 검증 -> 재발 방지`를 훈련시키는 데 초점을 둔다.

## Incident Brief

`토요일 저녁 7시 40분, 결제 승인 자체는 대부분 성공하지만 영수증 발행, 포인트 적립, 주문 상태 동기화 같은 후처리가 2분 이상 지연되기 시작했습니다. 후처리 큐 backlog는 평소 400건 수준에서 3만 2천 건까지 늘었고, consumer lag도 빠르게 커지고 있습니다. 외부 결제 승인 성공률은 아직 96% 이상이지만, 일부 사용자는 결제 직후 주문 내역이 비어 보이거나 포인트가 늦게 반영된다고 문의하고 있습니다. 지금은 프로모션 피크 시간대라 큐를 통째로 비우거나 무작정 재처리했다가 중복 적립과 상태 꼬임을 만들 위험이 있습니다. 이 상황에서 무엇을 먼저 확인하시겠습니까?`

## Realism Anchors

### Time Context

- `토요일 저녁 7시 40분`
- `프로모션 피크 시간대`
- `승인 성공 이후 후처리 지연이 10분 이상 지속`

### User Impact Surface

- 결제 직후 `주문 내역 확인`
- `영수증 발행`
- `포인트 적립`
- `주문 상태 반영`

핵심은 결제가 완전히 실패한 것이 아니라, `결제는 된 것 같은데 결과가 이상해 보이는` 신뢰 훼손 상황이라는 점이다.

### Measurable Symptoms

- 후처리 큐 backlog: `400 -> 32,000`
- consumer lag: `10초 이하 -> 11분`
- DLQ 유입량: `0~5건/분 -> 420건/분`
- 후처리 성공까지 걸리는 시간 p95: `4초 -> 145초`
- 결제 승인 성공률: `96% 이상으로 유지`

### Contradictory Clues

- 결제 승인 자체는 아직 대부분 성공하고 있다
- 앱 서버 CPU는 `55%` 수준으로 버티고 있다
- 장애처럼 보이지만, 실제로는 `동기 승인`과 `비동기 후처리`의 분리가 핵심이다

### Constraint

- 피크 시간대라 후처리를 오래 미루면 고객 불만이 폭발한다
- 큐 purge나 전량 재처리는 중복 적립, 상태 역전, 알림 중복을 만들 수 있다
- 일부 후처리는 파트너 정산이나 고객 공지와 연결되어 있어 단순 생략이 어렵다

### Risk Of The Wrong Move

- consumer를 무작정 늘리면 downstream DB나 external webhook 부하만 키울 수 있다
- 실패 건 전체 재처리는 중복 포인트 적립이나 중복 영수증 발행을 만들 수 있다
- 주문 상태 지연을 단순 UI 문제로 취급하면 정합성 검증 시점을 놓친다

## Starting States

### `대기열 정체`

- 짧은 설명: 밀린 작업이 길게 쌓이고 있다.
- 면접 의미: 무엇을 먼저 흘려보내고 무엇을 잠깐 늦춰도 되는지 판단해야 한다.

### `급한 불`

- 짧은 설명: 결제 후 체감 품질 저하로 신뢰가 흔들리고 있다.
- 면접 의미: 기술적 순수성보다 고객 영향과 핵심 후처리 우선순위가 중요하다.

### `압박감`

- 짧은 설명: 빠른 기준 수립과 설명이 필요하다.
- 면접 의미: 큐, lag, 재처리를 다 말하되 우선순위를 분명히 해야 한다.

## Turn 1

### State Reveal

- `정산 파이프라인 면접관이 승부를 걸어왔다!`
- `대기열 정체가 길게 늘어진다!`
- `후처리 큐 backlog가 3만 건을 넘겼다.`
- `급한 불이 번지고 있다!`
- `결제 직후 주문 내역이 비어 보인다는 문의가 빠르게 늘고 있다.`
- `압박감이 전장을 조인다!`
- `지금은 결제 실패와 후처리 지연을 정확히 구분해 말해야 한다.`

### Interviewer Attack

- `면접관의 추궁!`
- `"이 상황에서 가장 먼저 무엇을 구분하시겠습니까? 그리고 왜 그 순서가 중요하다고 보시나요?"`

### Candidate Actions

- `범위 파악`
- `우선순위 선언`
- `원인 분리`
- `의존성 점검`

### Strong Player Answer Example

`우선 결제 승인 자체가 실패하는 문제인지, 승인 이후 후처리만 늦는 문제인지부터 분리하겠습니다. 동시에 주문 상태 반영, 영수증, 포인트 적립 중 어떤 후처리가 고객 신뢰와 CS에 가장 큰 영향을 주는지 우선순위를 나눠서, 임계 후처리와 비임계 후처리를 구분하겠습니다.`

### Why This Is Strong

- 동기 승인과 비동기 후처리를 구분한다
- 고객이 체감하는 문제를 우선순위로 둔다
- `대기열 정체`를 단순 시스템 지표가 아니라 서비스 영향으로 번역한다

### Common Mistakes

- 결제 전체가 실패했다고 단정한다
- backlog 숫자만 보고 사용자 영향을 설명하지 않는다
- 어떤 후처리가 임계인지 구분하지 않는다
- 큐를 비우거나 재처리하자는 말을 너무 빨리 꺼낸다

### Follow-up Question 1

- `면접관의 되물림!`
- `"좋습니다. 그런데 지금 지연된 후처리 중 무엇을 먼저 살리고, 무엇은 잠시 늦춰도 된다고 보시나요?"`

## Turn 2

### New Reveal

- `추가 정보가 드러났다!`
- `포인트 적립 consumer가 최근 배포 후 배치 크기 설정 변경으로 처리량이 절반 이하로 떨어졌다.`
- `불길한 조짐이 보인다!`
- `일부 실패 건은 재시도 중이고, 같은 결제 ID로 이벤트가 두 번 이상 들어온 흔적도 보인다.`
- `협업 신호가 필요하다!`
- `고객센터는 주문 상태 지연과 포인트 누락 문의를 같이 받기 시작했다.`

### Interviewer Attack

- `면접관의 압박!`
- `"지금 어떤 회복 조치를 하시겠습니까? 다만 잘못 건드리면 중복 적립과 상태 꼬임이 생길 수 있습니다."`

### Candidate Actions

- `변경 추적`
- `우선 차단`
- `상황 공유`
- `협업 호출`

### Strong Player Answer Example

`우선 최근 설정 변경으로 처리량이 낮아진 consumer부터 원복하거나 배치 크기를 안전하게 조정하겠습니다. 동시에 포인트 적립처럼 중복 처리 위험이 큰 후처리는 멱등성 키 검증 없이 재처리하지 않고, 주문 상태 반영과 고객 확인에 필요한 임계 후처리를 우선 복구하겠습니다. 고객센터와 운영팀에도 지연 범위와 수동 보정이 필요한 유형을 바로 공유하겠습니다.`

### Why This Is Strong

- 처리량 회복과 정합성 보호를 동시에 본다
- 모든 재처리를 동일하게 다루지 않는다
- 임계 후처리와 비임계 후처리를 나눠 복구한다

### Common Mistakes

- consumer만 늘리면 된다고 본다
- 실패 건 전체 재처리를 바로 제안한다
- 멱등성이나 duplicate event를 언급하지 않는다
- 고객 공지나 운영 협업을 빼먹는다

### Follow-up Question 2

- `면접관의 되물림!`
- `"재처리가 꼭 필요하다면, 어떤 기준으로 안전한 재처리 대상을 나누시겠습니까?"`

## Turn 3

### New Reveal

- `복구 창이 열렸다!`
- `배치 크기를 조정하고 비임계 후처리를 잠시 늦추자 backlog 증가세는 멈췄다.`
- `가설이 정리된다!`
- `핵심 원인은 설정 변경으로 인한 consumer 처리량 저하와, 일부 이벤트의 중복 소비 안전장치 부족으로 보인다.`
- `불만 누적은 아직 남아 있다!`
- `지난 15분간 처리된 결제 중 일부는 포인트 적립 여부와 주문 상태를 다시 검증해야 한다.`

### Interviewer Attack

- `면접관의 마무리 승부수!`
- `"서비스를 안정화한 뒤, 무엇을 검증하고 무엇을 바꾸시겠습니까?"`

### Candidate Actions

- `관측 세우기`
- `사후 정리`
- `상황 공유`
- `협업 호출`

### Strong Player Answer Example

`우선 결제 ID 기준으로 주문 상태, 영수증 발행, 포인트 적립을 대조해 누락과 중복이 없는지 검증하겠습니다. 그다음 후처리별 멱등성 키 적용 여부, DLQ 기준, backlog와 consumer lag 알람, 임계 후처리 우선순위 정책을 보강하겠습니다. 고객센터에는 어떤 유형의 문의가 실제 장애인지와 수동 보정 대상 범위를 공유하고, 재발 방지를 위해 설정 변경 검증과 replay runbook도 정리하겠습니다.`

### Why This Is Strong

- 정합성 검증을 최우선 후속 과제로 둔다
- 멱등성, DLQ, replay 정책을 구조적으로 말한다
- 내부 개선과 고객 대응을 함께 포함한다

### Common Mistakes

- backlog만 줄면 끝났다고 본다
- 누락/중복 검증을 빼먹는다
- 설정 변경 검증과 replay 기준을 남기지 않는다
- 고객 신뢰 회복 방안을 언급하지 않는다

### Follow-up Question 3

- `면접관의 마지막 되물림!`
- `"다음에 같은 일이 나도, consumer를 늘리는 것보다 먼저 확인해야 할 한 가지를 꼽는다면 무엇입니까?"`

## Total Follow-up Count

- 총 `3개`
- 권장 리듬:
  - 1턴 후 1개
  - 2턴 후 1개
  - 3턴 후 1개

이 시나리오는 follow-up이 특히 중요하다. `큐가 쌓였다`는 표면 현상 뒤에 `무엇을 재처리하면 위험한가`를 묻는 순간 면접답게 변한다.

## Scoring Intent

이 시나리오에서 특히 높게 보는 포인트:

- `영향 파악`: 결제 승인과 후처리를 분리했는가
- `우선순위`: 임계 후처리와 비임계 후처리를 나눴는가
- `기술적 추론`: backlog, lag, duplicate risk, 멱등성을 연결했는가
- `대응 적합성`: 전량 재처리 대신 안전한 복구 기준을 말했는가
- `설명 명확성`: 고객 영향과 데이터 정합성을 함께 설명했는가

특히 가산점을 주는 신호:

- `주문 상태`, `영수증`, `포인트`를 같은 심각도로 보지 않음
- `duplicate event`, `멱등성 키`, `DLQ`, `replay safety`를 언급함
- 큐 적체를 단순 처리량 문제로만 보지 않고 신뢰 문제로 연결함

## Final Coaching Points

- 비동기 후처리 장애는 `큐가 쌓였다`보다 `무엇이 고객에게 잘못 보이는가`로 먼저 번역하는 답이 강하다.
- 재처리는 복구 수단이지만, 면접에서는 `무엇이 안전하게 재처리 가능한지`를 같이 말해야 점수가 오른다.
- 좋은 답변은 `영향 구분 -> 임계 후처리 복구 -> 정합성 검증 -> 멱등성/알람 강화` 흐름을 가진다.
